## Accounting needs a packet, not a screenshot

If payments ops sends only a transaction hash, controllers cannot close. Design the handoff as a packet that mirrors wire evidence: who approved, what invoice, which asset/network, what amount, when it confirmed, and how it posted.

## Minimum evidence checklist

1. Invoice PDF and payable ID.
2. Approval trail (maker-checker).
3. Destination address attestation.
4. Asset, network, and amount.
5. Transaction hash + explorer URL.
6. Timestamp of send and confirmation depth policy.
7. Supplier acknowledgment when available.
8. FX / conversion note if fiat was converted first.
9. GL account mapping.

| Evidence | System of record | Failure if missing |
| --- | --- | --- |
| Invoice | AP | Cannot match payable |
| Hash | Payments ops | Cannot prove settlement |
| Approval | Workflow tool | Control gap |
| Conversion note | Treasury | P&L unexplained |

## Reconciliation rhythm

Reconcile daily during pilots, then settle into a cadence that matches payable volume. Partial payments and overpayments need explicit rules — see [invoice field standards](/blog/invoice-reference-fields-for-crypto-payments/) once that guide is live, and keep memos consistent.

## Risks and limits

Chain explorers are not a substitute for internal approvals. Price moves between conversion and payment can create P&L noise if undocumented. Wrong-asset sends create hard-to-reverse incidents.

## Handoff SOP (numbered)

1. Ops closes the payable ticket.
2. Packet auto-assembles or is attached manually.
3. Accounting validates completeness.
4. Posting occurs with hash in the memo field.
5. Exceptions go to a named queue within SLA.
